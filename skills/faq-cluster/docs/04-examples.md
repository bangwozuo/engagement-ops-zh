# 使用示例

以下示例均来自 `examples/input.json` 的脚本实跑结果（退出码 0）。

## 示例 1：标准输入 —— 一周提问评论的聚类与 FAQ 榜

**输入**（节选）：

```json
{
  "account": "@小鹿的好物日记",
  "period": "2026-09-23 ~ 2026-09-29",
  "questions": ["在哪买", "在哪买啊", "姐妹在哪买", "求链接", "求个链接",
                "求链接！", "多少钱", "油皮能用吗"]
}
```

**输出**（脚本实跑）：23 条提问 → 13 簇，Top10 覆盖率 87%（判定正常）。
「在哪买/在哪买啊/姐妹在哪买」三问法经 bigram + 编辑距离比合并为频次 3 的单簇。

## 示例 2：整改前后对照 —— 从逐条回复到置顶 FAQ

**场景**：一周里「求链接/在哪买」类提问 6 条（占 26%），运营者逐条回「链接在小黄车」。

| 阶段 | 做法 |
|---|---|
| 改造前 | 每条手打回复，周末重复劳动，漏回 2 条被追问 |
| 聚类后 | 该簇进 FAQ Top10，标准答案要点自动生成；置顶评论 + 简介口径「购买链接都在小黄车 3 号位」 |
| 效果 | 下周同类提问降为 2 条（用户互相回答），省出回复时间做吐槽处理 |

## 示例 3：阈值的意义 —— 0.60 为什么不能随便降

**场景**：「油皮能用吗」vs「油皮会闷痘吗」相似度 0.55。

- 若阈值降到 0.50：两句被合并 → FAQ 答案是"适用性说明"，但第二句真正想问的是
  **致痘风险**，答案错配，用户二次追问
- 保持 0.60：两句分开，各自得到对口答案。**宁可漏合（多写一条 FAQ），
  不可错合（答案错配）**——这是合并阈值定 60% 的原因

## 示例 4：覆盖率自检发现问题过散

**输入**：某周 40 条提问，最长簇频次 2，Top10 覆盖率 42%。

**输出**：判定「分类有误/问题过散，需人工复核」。模型复核结论：该周是新品首发期，
提问围绕新品发散（颜色/价格/渠道/成分各成一簇），属正常发散——
**建议做一条「新品 Q&A 汇总置顶」**，而不是强行逐条写 FAQ。

## 示例 5：数据缺失的正确行为

**输入**：`questions: ["", "？？？", "这个"]`

**输出**：空串与无实义词被归一化过滤，汇总结论：
「3 条输入中 3 条无效（空/无实义词），请检查评论导出是否截断」——不猜问题内容、
不产出虚假榜单。
